# Drag-and-Drop Remediation Plan

*Generated: July 11, 2025*

## 1. Problem Statement

The current drag-and-drop (dnd) implementation using `@dnd-kit` for cards and lists suffers from a poor user experience. When an item is dragged and released, it visually "snaps back" to its original position before moving to its new location. This creates a jarring visual glitch that makes the interface feel unresponsive and buggy.

## 2. Analysis of Current Implementation

-   **Components Involved**: The dnd logic is primarily located in `src/frontend/src/pages/BoardDetailPage.tsx` (which likely holds the `DndContext`), `src/frontend/src/components/kanban/List.tsx` (as a sortable container), and `src/frontend/src/components/kanban/Card.tsx` (as the draggable item).
-   **Likely Cause**: The "snap-back" effect is characteristic of a dnd implementation that does not use a `DragOverlay`. Without it, the original DOM element is transformed, and when the underlying state changes, React re-renders, causing the element to briefly revert to its pre-drag position before the new position is painted.
-   **Testing Gap**: As noted, there are no E2E tests in Playwright specifically for dnd functionality. While backend integration tests for move operations exist, they do not validate the frontend user experience.

## 3. Comparison with @dnd-kit Best Practices

The `@dnd-kit` documentation recommends several patterns for a smooth and accessible experience that we can adopt:

-   **`<DragOverlay>`**: This is the most critical component for fixing the visual glitches. It renders the dragged item inside a portal, completely separate from its original parent. This prevents the item from being affected by layout changes in the source container, resulting in a smooth drag motion from start to finish.
-   **Sensors**: For robust input support, `useSensors` should be configured with `PointerSensor` (for mouse and touch) and `KeyboardSensor` (for accessibility).
-   **State Management**: The `onDragEnd` event handler must robustly handle two distinct scenarios: reordering an item within the same list and moving an item to a different list. This logic should trigger optimistic updates in the Redux store to ensure the UI feels instantaneous.
-   **Accessibility**: Using `KeyboardSensor` and ensuring proper ARIA attributes are applied to draggable elements and drop zones is crucial for users relying on assistive technologies.

## 4. Implementation Steps

The remediation will focus on refactoring the existing dnd code to incorporate these best practices.

1.  **Implement `<DragOverlay>` in `BoardDetailPage.tsx`**:
    -   Add state to track the currently active dragged item (`const [activeId, setActiveId] = useState<string | null>(null);`).
    -   Use the `onDragStart` event to set the `activeId`.
    -   Wrap the main board view with `<DndContext>` and add a `<DragOverlay>` component alongside it.
    -   Inside the `<DragOverlay>`, render a `Card` component when `activeId` is set. This ensures the dragged item is rendered in a portal.
    -   Use the `onDragEnd` event to clear the `activeId`.

2.  **Refine the `onDragEnd` Handler**:
    -   Ensure the logic correctly distinguishes between a card being reordered within its list and being moved to a new list by comparing `active.data.current.sortable.containerId` and `over.data.current.sortable.containerId`.
    -   Dispatch the appropriate RTK Query mutation for each case (`moveCard` or `reorderCard`).
    -   Ensure the mutations perform optimistic updates as defined in the architecture docs to provide immediate UI feedback.

3.  **Configure Sensors for Better Input**:
    -   In `BoardDetailPage.tsx`, define sensors using `useSensors` to include `PointerSensor` and `KeyboardSensor`.
    -   Pass the configured sensors to the `<DndContext>` provider. This will enable keyboard-based dnd and improve touch interactions.

4.  **Ensure Accessibility**:
    -   Verify that `useSortable` is correctly passing ARIA attributes to the draggable `Card` components.
    -   The `KeyboardSensor` will provide the necessary screen reader announcements and keyboard controls.

## 5. Testing Strategy

To prevent regressions and validate the fix, a multi-layered testing approach is required.

1.  **Unit Tests (Vitest)**:
    -   While not the primary focus, any complex position-calculation logic used for optimistic updates should be extracted into a utility function and unit-tested.

2.  **E2E Tests (Playwright)**:
    -   **This is the highest priority.** Create a new test file: `tests/e2e/dnd.spec.ts`.
    -   **Test Case 1: Reorder Card in List**:
        -   Navigate to a board.
        -   Use `page.dragTo()` to move a card to a new position within the same list.
        -   Assert that the card is in the new position visually.
        -   Reload the page and assert the position is persisted.
    -   **Test Case 2: Move Card Between Lists**:
        -   Use `page.dragTo()` to move a card from one list to another.
        -   Assert the card appears in the new list.
        -   Reload the page and assert the move is persisted.

## 6. Risks & Mitigation

-   **Risk**: Refactoring dnd logic is complex and could introduce new bugs.
-   **Mitigation**: Implement the Playwright E2E tests *before* starting the refactor. This creates a safety net to validate that the core functionality is not broken during the process.

By following this plan, we can resolve the visual glitches, create a smooth and professional dnd experience, and establish a robust testing strategy to maintain it.
